WEEK 2: HNSW RETRIEVAL PERFORMANCE BENCHMARK

1. INTRODUCTION

The objective of Week 2 was to develop and evaluate the vector retrieval system for the complete Flickr30k image dataset. The main focus was on generating CLIP image embeddings, building FAISS vector indexes, implementing text-to-image retrieval, and comparing approximate HNSW search with exact FlatIP search.

During this week, all 31,783 images in the Flickr30k dataset were successfully processed. Each image was converted into a 512-dimensional CLIP embedding. These embeddings were normalized and indexed using two FAISS retrieval methods: FlatIP and HNSW.

FlatIP was used as the exact search method and served as the ground truth for evaluating the HNSW approximate search method. The performance of HNSW was evaluated using Recall@5 for different values of the efSearch parameter.

4. CLIP EMBEDDING GENERATION

The project uses the pretrained CLIP model:

openai/clip-vit-base-patch32

CLIP is a multimodal model that maps images and text into a shared embedding space. This allows a text query and an image to be compared using their vector representations.

For every image in the Flickr30k dataset, the image was passed through the CLIP image encoder to generate a 512-dimensional vector.

The process can be represented as:

Image → CLIP Image Encoder → 512-Dimensional Embedding

After processing the complete dataset, the final embedding matrix had the following shape:

(31783, 512)

This means that there were 31,783 image embeddings, with each image represented by 512 numerical features.

5. EMBEDDING NORMALIZATION

The generated image embeddings were L2-normalized before performing similarity search.

Normalization converts the embeddings into unit-length vectors. This is important because the project uses inner-product similarity for retrieval.

For normalized vectors, the inner product is equivalent to cosine similarity.

The relationship can be represented as:

Cosine Similarity(x, y) = x · y

when both x and y are normalized.

Therefore, FAISS IndexFlatIP can be used to perform cosine-similarity-based image retrieval.

The normalization validation was successfully completed.

Result:

Normalization: PASSED

6. METADATA ALIGNMENT

Metadata alignment was also verified during the Week 2 process.

The purpose of metadata alignment is to ensure that each embedding corresponds to the correct image and metadata record.

The expected relationship is:

Embedding[i] ↔ Metadata[i] ↔ Image[i]

Correct alignment is important because an incorrect mapping could cause the retrieval system to return the wrong image even if the similarity search itself is correct.

The metadata alignment check was successfully completed.

Result:

Metadata Alignment: PASSED

7. FAISS VECTOR INDEXING

FAISS was used as the vector search library.

Two different FAISS indexes were created:

1. FAISS FlatIP
2. FAISS HNSW

The purpose of using two different indexes was to compare exact vector search with approximate vector search.

8. FAISS FLATIP

FAISS IndexFlatIP was used as the exact search index.

FlatIP compares the query vector with every vector stored in the database and calculates the similarity between them.

The search process can be represented as:

Query
↓
Compare with all 31,783 image embeddings
↓
Calculate similarity
↓
Select the highest similarity vectors
↓
Return Top-K images

Since FlatIP checks every vector, it provides exact nearest-neighbor results.

Therefore, FlatIP was selected as the ground truth for evaluating the HNSW index.

Result:

FlatIP vectors: 31,783

9. FAISS HNSW

HNSW stands for Hierarchical Navigable Small World.

HNSW is an approximate nearest-neighbor search algorithm. Instead of comparing the query with every vector, it uses a graph structure to efficiently navigate through promising neighboring vectors.

The general search process is:

Query
↓
Enter HNSW graph
↓
Explore promising neighbors
↓
Find nearest candidate vectors
↓
Return Top-K results

The advantage of HNSW is that it can perform vector search efficiently on large datasets while maintaining high retrieval accuracy.

Result:

HNSW vectors: 31,783

The text query is converted into a CLIP text embedding.

The retrieval process is:

Text Query

Top-K Similar Images

During the Week 2 benchmark, 10 text query embeddings were generated.

The query embedding matrix had the shape:

(10, 512)

This confirms that all 10 queries were successfully converted into 512-dimensional CLIP embeddings.

11. GROUND TRUTH GENERATION

To evaluate HNSW, exact search was first performed using the FlatIP index.

Because FlatIP compares the query against all vectors, its results were considered the exact nearest neighbors for this experiment.

The evaluation process was:

Text Query
↓
CLIP Text Embedding
↓
FlatIP Search
↓
Exact Top-5 Results
↓
Ground Truth

The HNSW results were then compared against these FlatIP results.

This allowed the retrieval accuracy of HNSW to be measured using Recall@5.

12. RECALL@5

Recall@5 was used as the primary evaluation metric.

Recall@5 measures how many of the true Top-5 results from the exact FlatIP search are also retrieved by HNSW.

For example, suppose FlatIP returns the following Top-5 images:

A, B, C, D, E

and HNSW returns:

A, B, C, X, Y

Then three of the five correct results were retrieved.

Therefore:

Recall@5 = 3 / 5 = 60%

In this benchmark, Recall@5 was calculated across the 10 text queries.

A higher Recall@5 indicates that HNSW is producing results that are closer to the exact FlatIP results.

13. HNSW PERFORMANCE BENCHMARK

The main parameter evaluated during the experiment was efSearch.

efSearch controls how extensively the HNSW graph is searched during a query.

Different efSearch values were tested:

efSearch = 16
efSearch = 32
efSearch = 64
efSearch = 128
efSearch = 256

The benchmark produced the following results:

At efSearch = 16:

Recall@5 = 86%

At efSearch = 32:

Recall@5 = 94%

Average Search Time = 0.336 ms

At efSearch = 64:

Recall@5 = 96%

Recall@5 = 100%

14. EFFECT OF efSearch ON RETRIEVAL ACCURACY

The experiment clearly showed that increasing efSearch improved the retrieval accuracy of HNSW.

The Recall@5 values changed as follows:

86% → 94% → 96% → 100% → 100%

for efSearch values:

16 → 32 → 64 → 128 → 256

At lower efSearch values, HNSW explores fewer candidate vectors. Because of this, some of the exact nearest neighbors may not be discovered.

As efSearch increases, HNSW explores more candidate vectors. This increases the probability of finding the correct nearest neighbors.

Therefore:

Higher efSearch → More graph exploration → Higher retrieval recall

15. EFFECT OF efSearch ON SEARCH TIME

Increasing efSearch also increased the average search time.

The measured search times were:

efSearch = 16 → 0.236 ms

efSearch = 32 → 0.336 ms

efSearch = 64 → 0.514 ms

efSearch = 128 → 0.994 ms

efSearch = 256 → 2.115 ms

This demonstrates that increasing search accuracy comes with an increase in search cost.

The relationship can be summarized as:

efSearch increases
↓
More candidates are explored
↓
Search takes more time
↓
Potentially better recall

16. BEST TESTED CONFIGURATION

The benchmark achieved 100% Recall@5 at efSearch = 128.

The results were:

Recall@5 = 100%

Average Search Time = approximately 0.994 ms

When efSearch was increased from 128 to 256, Recall@5 remained at 100%.

However, the average search time increased from approximately 0.994 ms to 2.115 ms.

Therefore, within the configurations tested in this benchmark, efSearch = 128 achieved the same measured Recall@5 as efSearch = 256 with a lower measured average search time.

17. IMPORTANT HNSW PARAMETERS

Three important HNSW parameters relevant to this project are M, efConstruction, and efSearch.

17.1 M

M controls the number of connections or neighbors maintained for nodes in the HNSW graph.

Increasing M generally results in a more highly connected graph.

A higher M can potentially improve search quality, but it also increases memory usage and index construction requirements.

17.2 efConstruction

efConstruction controls how extensively the graph is explored during the construction of the HNSW index.

A higher efConstruction value generally requires more computation during index construction but can result in a better-quality graph.

The general relationship is:

Higher efConstruction
→ More construction effort
→ Potentially better graph quality
→ Higher construction cost

17.3 efSearch

efSearch controls how extensively the HNSW graph is explored during search.

This was the main parameter evaluated in the Week 2 benchmark.

The general relationship is:

Low efSearch
→ Faster search
→ Potentially lower recall

High efSearch
→ More exploration
→ Potentially higher recall
→ Higher search time
